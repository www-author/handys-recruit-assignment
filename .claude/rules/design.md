# 설계 지침

기능의 판정 조건·API 계약은 루트 README.md를 따른다. 이 파일은 구현 구조와 일관성 원칙을 정의한다.

## 구조

- 단일 애플리케이션 모듈에서 Controller–Service–Repository 흐름을 사용한다.
- Controller는 요청 검증과 응답 변환을, Service는 유스케이스와 트랜잭션을, Repository는 영속성 접근을 담당한다.
- 시간과 예약 상태의 판정은 웹·DB에 의존하지 않는 정책으로 분리한다. 정책에 엔티티의 지연 로딩이나 시스템 시각 읽기를 숨기지 않는다.
- 요청·응답 DTO와 JPA 엔티티를 분리한다. 엔티티를 API 응답으로 직접 반환하지 않는다.
- 호출부 하나를 위한 서비스 인터페이스, 범용 기반 클래스, 이벤트 버스, 추가 모듈을 선제적으로 만들지 않는다.

## 데이터·시간·트랜잭션

- 예약과 청소 작업을 별도로 저장한다. 청소 작업의 예약 ID에 유일 제약과 외래 키를 적용하여 예약당 최대 한 작업을 보장한다.
- 완료 상태는 해당 입실 예약의 작업에 귀속한다. 이전 투숙의 객실 상태를 재사용하지 않는다.
- 서비스에 Clock을 주입한다. 시각은 Instant로 다루며 날짜 경계는 명시적인 지점 ZoneId로 계산한다. 서버 기본 시간대에 의존하지 않는다.
- 요청당 얻은 동일 시각을 조회 범위와 정책 판정에 전달한다. 서울의 오늘 구간은 시작 포함·다음 날 시작 제외로 계산한다.
- 완료 처리 트랜잭션에서 PENDING인 행만 COMPLETED로 바꾸고 completedAt을 함께 설정하는 조건부 갱신을 사용한다. 결과를 재조회하여 반복·동시 요청에 같은 최초 완료 시각을 반환한다.
- 조건부 벌크 갱신을 쓰면 영속성 컨텍스트의 오래된 엔티티를 반환하지 않도록 비우거나 새 상태를 조회한다. 조회 후 무조건 save하는 방식으로 최초 완료 시각을 덮어쓰지 않는다.
- 조회는 읽기 전용 트랜잭션을 사용한다. 예약별 개별 조회를 반복하는 N+1 접근을 피한다.
- 청소 작업 없음은 조회 시 표현할 정상 상태다. 읽기 요청에 데이터 생성·수정 부작용을 넣지 않는다.
