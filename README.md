# 체크인 준비 확인 API

체크인이 임박했지만 청소 완료가 확인되지 않은 예약을 찾아주는 작은 운영 API입니다.

## 문제와 가정

지점 운영 담당자가 당일 입실 예약과 청소 현황을 수기로 대조한다고 가정합니다. 전체 예약을 반복해서 확인하는 대신, 확인이 필요한 예약과 사유를 제공하여 대조 업무를 줄이는 것이 목적입니다.

이는 실제 핸디즈에서 확인된 문제가 아닌 과제용 가정입니다. 한 지점, `Asia/Seoul`, 체크인 60분 전이라는 기준도 시연용 정책입니다. 청소 미완료는 실제 체크인 지연을 확정하는 정보가 아닙니다.

## 문제를 작게 나눈 방식과 근거

숙박 운영 전체에서 **입실 전에 확인이 필요한 예약을 식별하는 단계**를 분리했습니다. 운영 담당자가 내려야 하는 판단을 “오늘 체크인이 임박한 예약 중 청소 완료가 확인되지 않은 예약은 무엇인가?”라는 한 가지 질문으로 좁혔습니다.

- **사용자와 시점:** 당일 입실 준비 상태를 확인하는 지점 운영 담당자를 대상으로 합니다.
- **판단에 필요한 정보:** 예약 상태, 체크인 예정 시각, 해당 입실 예약의 청소 상태만 사용합니다. 세 정보를 대조하면 확인 대상을 구분할 수 있다고 판단했습니다.
- **처리 단위:** 객실 자체가 아닌 입실 예약 한 건을 기준으로 삼았습니다. 같은 객실의 이전 투숙에 대한 청소 완료가 이번 입실 준비 완료로 오인되는 것을 방지하기 위해서입니다.
- **제공할 결과:** 청소 미완료와 청소 상태 미확인을 구분하고, 체크인 예정 시각이 빠른 순서로 보여줍니다. 작업 기록이 없는 경우도 확인 대상으로 남겨 누락을 숨기지 않습니다.

문제의 범위를 이렇게 정한 근거는 전체 예약을 반복해서 대조하는 과정에서 확인 누락이 생길 수 있다는 가정입니다. 확인이 필요한 항목과 사유를 모아 제공하면 담당자가 살펴볼 대상을 좁힐 수 있습니다. 실제 업무 시간 절감 효과는 측정하지 않았으며, 운영자 사용 전후 비교가 필요합니다.

## 구현 범위의 판단

| 포함한 범위 | 판단 근거 |
| --- | --- |
| 확인 대상 조회 | 예약과 청소 현황을 대조하는 반복 업무를 직접 줄이는 기능이기 때문입니다. |
| 청소 완료 처리 | 담당자가 확인한 결과를 반영하고, 처리한 예약이 확인 대상에서 빠지는 흐름까지 제공하기 위해서입니다. |
| 다양한 상태의 샘플 데이터와 핵심 테스트 | 외부 시스템 없이 정상·누락·시간 경계·중복 요청 상황을 재현하고 판단 규칙을 확인하기 위해서입니다. |

예약·청소 작업 생성과 청소 인력 배정은 별도의 업무이므로 제외했습니다. 예약과 청소 작업은 이미 존재하는 입력으로 보고 샘플 데이터로 준비했습니다.

프론트엔드, 인증, OTA 연동, 알림, 스케줄러, 배포도 제외했습니다. 이번 구현에서는 **확인 대상 조회 → 청소 완료 반영 → 확인 대상에서 제외**되는 흐름에 집중했습니다. 외부 연동이나 알림 전달 방식보다 어떤 예약을 확인 대상으로 판단할지가 먼저 정해져야 한다고 보았습니다. 운영 환경에 바로 배포할 서비스는 이번 범위에 포함하지 않습니다.

## 핵심 동작과 API

요청마다 주입된 `Clock`에서 현재 시각을 한 번 읽습니다. 서울 기준 오늘 체크인 예정인 `RESERVED` 예약 중 `scheduledCheckInAt <= now + 60분`이고 청소 완료가 확인되지 않은 항목을 조회합니다.

- 오늘 예정 시각이 이미 지난 예약도 포함합니다. `CANCELLED`, `CHECKED_IN`, 다른 날짜 예약은 제외합니다.
- 청소 작업은 입실 예약당 최대 하나입니다. 같은 객실의 이전 예약에 대한 청소 완료 상태를 재사용하지 않습니다.
- 작업이 `PENDING`이면 `CLEANING_PENDING`, 작업 자체가 없으면 `CLEANING_STATUS_UNKNOWN`입니다. `COMPLETED`는 제외합니다.
- 예정 시각 경과 여부는 `scheduledCheckInAt < now`로 판정합니다. 예정 시각과 현재 시각이 같으면 경과하지 않은 것으로 봅니다.
- 결과는 예정 시각 오름차순, 예약 ID 오름차순으로 정렬합니다. 결과가 없으면 200과 빈 목록을 반환합니다.

| API | 요청과 응답 계약 |
| --- | --- |
| `GET /ops/check-in-risks` | 요청 본문·쿼리 없음. 200으로 `evaluatedAt`, `items` 반환. 각 항목은 `reservationId`, `roomNumber`, `scheduledCheckInAt`, nullable `cleaningTaskId`, `reason`, `overdue` 포함 |
| `PATCH /cleaning-tasks/{id}/complete` | 요청 본문 없음. 200으로 `id`, `status: COMPLETED`, `completedAt` 반환. 반복·동시 요청에서도 최초 완료 시각 유지 |

ID는 양의 Long으로 정의합니다. 잘못된 형식·범위의 ID는 400, 유효한 ID에 해당하는 청소 작업이 없으면 404로 응답합니다. 목록에서 청소 작업이 없는 경우는 정상적인 확인 대상이며, 조회 오류가 아닙니다. 완료 API는 누락된 작업을 새로 생성하지 않습니다.

시각은 내부적으로 `Instant`로 다루고, API에서는 `+09:00` 오프셋을 포함하는 ISO 8601 문자열로 표현합니다. 조회 결과는 `evaluatedAt` 기준이며, 응답 이후의 상태 변경까지 보장하지 않습니다.

## 설계 선택

메인 코드와 테스트의 기본 패키지 및 Gradle group은 `com.handys.assignment`로 통일합니다.

| 선택 | 이유 |
| --- | --- |
| 단일 모듈, Controller–Service–Repository | 두 API의 흐름을 쉽게 이해하고 불필요한 계층·추상화 비용을 줄임 |
| 독립적인 판정 정책과 주입된 Clock | 웹·DB 없이 시간 경계와 제외 조건을 재현 가능하게 검증 |
| 예약과 청소 작업 분리, 예약 ID 유일 제약 | 청소 상태 미확인을 표현하고 다른 투숙의 완료 상태 재사용을 방지 |
| 서비스 트랜잭션과 조건부 완료 갱신 | 동시 요청에서도 최초 완료 시각이 덮어써지지 않도록 처리 |
| H2 메모리 DB | 외부 DB 설치 없이 시연. 재시작 시 데이터 초기화 |

기술 기준은 JDK 21, Kotlin 2.3.21, Spring Boot 4.1.1, Gradle 9.7.1 Kotlin DSL, Spring MVC·Data JPA·Validation, H2, JUnit Jupiter·MockMvc입니다. 상세 지침은 [기술 스택 규칙](.claude/rules/tech-stack.md)에 둡니다.
